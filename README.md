# onelastleaf Haskell plugin SDK

Build trusted [onelastleaf](https://github.com/onelastleaf/onelastleaf) plugins
in Haskell. The SDK takes care of the long-lived local gRPC session, the
handshake with oll, concurrent jobs, cancellation, host calls, logs, and
artifact uploads. You provide the actions that your plugin should run.

## Build and test the SDK

You need GHC 9.2 or newer, `cabal-install`, `pkg-config`, the `protoc`
compiler, and the Snappy C library. This package is tested with GHC 9.6.7,
which also matches the projects generated by current versions of oll. The
SDK's protocol modules are already checked in, so you do not need to regenerate
them before building. However, a clean build still uses `protoc` while building
`proto-lens-protobuf-types`. The project also keeps Grapesy's Snappy compression
support enabled and uses `pkg-config` to locate the native library.

On Ubuntu or Debian, install the native dependencies with:

```console
sudo apt-get update
sudo apt-get install libsnappy-dev pkg-config protobuf-compiler
```

On macOS with Homebrew, use:

```console
brew install pkgconf protobuf snappy
```

On Windows, install the UCRT64 packages from MSYS2 and make sure its `bin`
directory is on `PATH` when you run Cabal:

```console
pacman -S mingw-w64-ucrt-x86_64-pkgconf \
  mingw-w64-ucrt-x86_64-protobuf \
  mingw-w64-ucrt-x86_64-snappy
```

Other systems need equivalent packages that provide `protoc`, `pkg-config`,
and `snappy.pc` for a linkable `libsnappy`.

From this repository:

```console
cabal update
cabal build all
cabal test all
```

`cabal update` is only needed when your local package index is missing or out of
date. The unit tests do not need a running oll daemon.

The `conformance` executable is a real plugin fixture, so running it by itself
is not useful: it expects oll to supply its endpoint and protocol messages. If
you also have the oll source tree, you can exercise the complete SDK protocol
instead:

```console
# Run in this repository first and copy the path it prints.
cabal build exe:conformance
cabal list-bin exe:conformance

# Then run in the onelastleaf repository, substituting that absolute path.
OLL_SDK_CONFORMANCE_PROGRAM=/absolute/path/to/conformance \
  cargo test --test plugin_sdk_conformance \
  external_sdk_obeys_the_plugin_protocol -- --ignored --exact
```

That test starts the fixture, provides the same loopback transport and stdin
liveness pipe used in production, and checks jobs, cancellation, host calls,
logs, artifacts, shutdown, and protocol failures.

## Create a plugin

The easiest route is to let oll generate a complete project:

```console
oll plugin new hello-haskell --language haskell \
  --id com.example.hello --name hello-haskell
cd hello-haskell
cabal build all
cabal test all
```

The generated project includes an `echo` action, its test, a Cabal package, and
the `oll.toml` recipe that tells oll how to build and launch it. Its Cabal file
depends on `onelastleaf-plugin-sdk ==0.1.0`.

`oll.toml` is the handoff between the project and oll. The generated manifest
explicitly selects `checkout = "install"`. This is a publisher-owned template
choice, not language detection inside oll, and a user mask cannot override it.
`oll plugin new` only writes the project files; it does not run Cabal, clone a
repository, contact the daemon, or access the network.

During a source install, update, or reconciliation, oll first uses an internal
temporary clone to resolve the plugin ID and manifest; that directory is not
exposed as a recipe placeholder. It then places the complete checkout in a
candidate `{install}` tree, runs `cabal install` there, and copies the executable
into that tree. oll validates the result, renames the whole tree once into its
final UUID-named generation, and only then atomically switches `current`. Source
steps and runtime argv may use `{install}` and `{mask_dir}`; `{source}` and
`{generation}` are deliberately not available in this checkout mode.

Consequently, every retained file must remain valid after the candidate is
renamed. The generated plugin launches the copied executable and is compatible
with that rule. A custom build that persists the candidate's absolute path—for
example in runtime data-file configuration—is not; make those paths relocatable
or explicitly select `checkout = "generation"` and use `{generation}`. The full
checkout, including `.git`, Cabal build output, and the copied executable,
remains in the installed generation, so do not put secrets in the repository
and account for those files when estimating disk use. Release-mode installation
ignores `source.checkout` and still requires a relocatable published artifact.

If you are changing this SDK and want the plugin to use your local checkout,
add the checkout to the plugin's `cabal.project`:

```cabal
packages:
  .
  /absolute/path/to/haskell-plugin-sdk
```

This override is for local development. oll builds an installed plugin from an
isolated Git checkout, so a machine-local path outside the plugin repository is
not available there. Before installing through oll, use the published SDK
package or a pinned, remotely accessible `source-repository-package` in the
plugin's `cabal.project`.

## Write an action

A small plugin can live entirely in `Main.hs`:

```haskell
{-# LANGUAGE OverloadedStrings #-}

module Main (main) where

import qualified Data.Text as Text
import Onelastleaf.PluginSDK

main :: IO ()
main = either (fail . Text.unpack) runPlugin $ do
  plugin <- newPlugin "com.example.hello" "0.1.0"
  addAction
    (Action "echo" "Return the supplied arguments" $ \_ arguments ->
      pure (stringResult (Text.unwords arguments)))
    plugin
```

The ID passed to `newPlugin` must be the same immutable ID declared in
`oll.toml`. Action handlers receive an `ActionContext` and a list of text
arguments. They can return string, Boolean, or integer results with the helper
functions exported by `Onelastleaf.PluginSDK`.

Long-running handlers should call `isCancelled` or `checkCancellation`
regularly. The context also gives you the job ID, trace, and deadline. Use
`getPluginConfig`, `invokePluginConfigFunction`, `callHost`, `logMessage`, and
`uploadArtifact` when the action needs an oll-owned capability. Host capability
failures throw `HostError`, whose structured protocol error can be inspected or
caught by the action; an uncaught `HostError` becomes that job's failure without
losing its code or retryability metadata.

## Install and call the plugin

oll installs plugins from Git. Commit the generated project and push it to a
remote that the oll daemon can read. The commands below use the daemon's Admin
API. If this is your first time running oll, complete the main project's
[quick start](https://github.com/onelastleaf/onelastleaf#quick-start) first:
initialize the node, add its generated network key to `config.lua`, and start
the daemon. Then install the plugin:

```console
oll start
oll plugin install <git-remote> --source
oll plugin start com.example.hello
oll plugin info com.example.hello
```

`oll plugin new` does not need the daemon, but installation and runtime commands
do. After `plugin start`, wait until `plugin info` reports the process state as
`ready`, then call the action:

```console
oll plugin call com.example.hello echo -- hello from Haskell
oll job info <job-id>
oll plugin log com.example.hello
```

`plugin call` returns after the plugin accepts the job and prints its JobId; it
does not wait for the action to finish. Use that ID with `job info`. Once the
job succeeds, its result is `hello from Haskell`. You can use either the
immutable plugin ID or its current unique name in the plugin commands.

After publishing another commit, update the installed generation explicitly:

```console
oll plugin update com.example.hello
oll plugin restart com.example.hello
```

An update intentionally does not restart a running plugin. Stop it later with
`oll plugin stop com.example.hello`, or remove its declaration, installed data,
and desired state with `oll plugin remove com.example.hello`.

## What happens at runtime

Do not set `OLL_PLUGIN_ENDPOINT` yourself. When oll starts the plugin, oll opens
an ephemeral loopback gRPC server, sets that environment variable, and keeps
the plugin's stdin open as a parent-liveness pipe. `runPlugin` validates the
endpoint, connects as the gRPC client, completes the handshake, and dispatches
jobs to your actions. If stdin reaches EOF, the SDK exits because the parent is
gone.

Plugin configuration stays in oll and is requested through the host-call API;
it is not copied into arbitrary files for the plugin to load. Plugin stdout and
stderr are captured in the per-plugin logs.

The plugin protocol does not impose an SDK-level envelope size cap. Grapesy
uses the size representable by gRPC framing rather than retaining a smaller
default such as 4 MiB. Artifact data remains bounded by the chunk limit oll
advertises in `HostHello` and is always sent through the chunked transfer API.

## Protocol changes

Generated Haskell modules are checked in under `generated/`; their canonical
definitions live under `proto/`. After changing the protocol, regenerate the
modules with `proto-lens-protoc` before publishing.

This SDK never computes, embeds, publishes, or compares a protobuf schema hash
or fingerprint. Descriptor-wide hashes change for compatible additions and
unrelated services, so they reject valid peers. Protocol changes instead
preserve field numbers and wire types, give additions safe absent semantics,
and tolerate unknown fields. Exact SDK pins provide reproducible builds; they
are not protobuf API versioning.
